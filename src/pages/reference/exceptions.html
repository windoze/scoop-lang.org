异常与资源

Scoop 的 throw、try、catch、finally 与 Kotlin 一致，没有受检异常。托管对象由 GC 回收，而文件、套接字等原生资源通过 Closeable 与 use 确定性地释放。

异常类型

所有可以抛出的值都是 Throwable 的子类型。Exception 是通用的异常基类，带有一个可选消息 message: String?。核心库提供以下异常：

异常抛出场景
UnwrapException对 None 使用 !!
ClassCastExceptionas 转换失败
ArithmeticException整数除以零或对零取余
IndexOutOfBoundsException数组、列表或字符串下标越界
IllegalArgumentException(message)实参不满足 API 的前置条件，例如负的数组长度、非正的区间步长
IllegalStateException(message)状态协议被破坏，例如初始化循环、重复恢复 continuation
CharacterCodingException严格 UTF-8 解码失败，byteOffset 给出首个非法字节的位置
ResourceUseExceptionuse 的正文与清理都失败，见use
MissingContextException缺少所需的 task-local Context 绑定
CancellationException协程被取消，见取消

除 Throwable 与 Exception 外，核心库的异常类都是 final 的。自定义异常通常继承 Exception，也可以直接继承 Throwable：

class ValidationError(val field: String, message: String) : Exception(Some(message))

fun checkAge(age: Int): Int {
    if (age < 0) throw ValidationError("age", "must not be negative")
    return age
}

fun main() {
    try {
        checkAge(-1)
    } catch (e: ValidationError) {
        println(f"${e.field}: ${e.message ?: "(no message)"}")
    }
}

泛型 class 也可以继承 Throwable；每个完整的类型实参是不同的异常类型，catch (e: Failure<Int>) 只捕获该 application 及其子类。

throw

throw e 抛出一个 Throwable 子类型的对象，表达式本身的类型是 Nothing，因此可以用在 Elvis 右侧或分支中。抛出与捕获传递的是同一个对象：重新抛出、跨协程保存后再抛出都保持对象的 identity。

try、catch 与 finally

  • 多个 catch 按书写顺序匹配；若前面的 catch 类型是后面某个的父类型（或相同），后者不可达，是编译错误。
  • catch 绑定的异常对象是普通的值，可以存储、返回或捕获到闭包中。
  • finally 在离开 try 时总是执行一次：正常结束、return、break、continue 或异常。finally 正常结束后，原来的动作（返回值、异常或跳转）继续进行；若 finally 自己执行了 return、throw、break 或 continue，新的动作会取代原来的动作。
  • 协程挂起不算离开，不会执行 finally；恢复时以异常失败等价于在原挂起点抛出。
  • try 是表达式，见 try 表达式。
fun first(): Int {
    try {
        return 1
    } finally {
        println("cleanup")          // 先执行，然后才返回 1
    }
}

fun overridden(): Int {
    try {
        throw IllegalStateException(Some("lost"))
    } finally {
        return 2                    // finally 中的 return 取代了异常
    }
}

fun main() {
    println(first())
    println(overridden())
}

栈快照

Throwable.printStackTrace() 向 stderr 输出异常的动态类型及其首次抛出时的调用栈。栈在 throw 时采集，而不是在构造或打印时；之后的重新抛出保留原来的快照。

  • 是否采集由链接选项 --enable-stack-trace[=true|false] 控制：debug 构建默认开启，release 构建默认关闭。关闭时不采集也不分配快照，printStackTrace() 输出 <stack trace unavailable: disabled>。
  • 有调试信息时显示源码位置（macOS 的 dSYM、Linux 的 .debug 或 Windows 的 PDB）；缺少符号时降级为模块与地址。异常的传播与捕获不受影响。
  • 栈快照反映物理调用栈，跨挂起点的逻辑调用链不会被还原。输出的具体格式不属于稳定接口。

未捕获异常与退出

异常逃出 main（或顶层属性初始化）时，程序向 stderr 输出异常类型和已有的栈快照，刷新输出后以退出码 1 结束。语言级 trap（例如运行时检测到的致命错误）同样以退出码 1 结束，它不是可捕获的异常，不执行 finally。

$ scoop run --release boom.scoop; echo "exit=$?"
scoop: uncaught exception: …IllegalStateException
  <stack trace unavailable: disabled>
exit=1

exit(code: Int): Nothing 刷新 stdout/stderr 后立即结束整个进程。它不展开调用栈，不执行 finally、release 块，也不等待其他线程。POSIX 系统上父进程通常只能看到退出码的低 8 位，Windows 保留完整的 32 位值。正常结束时的退出码由 main 的签名决定，见程序入口。

Option 还是异常

标准库的约定：预期中可能失败的查询与解析同时提供抛出异常的版本和返回 Option 的 …OrNone 版本，例如 toInt() 与 toIntOrNone()、String.fromUtf8 与 String.fromUtf8OrNone。调用方能够处理“没有结果”时使用 Option 版本；违反前置条件属于程序错误时使用异常。scoop.std 还提供 Result<T, E> 与 runCatching，用于把异常转为值。

确定性资源释放

核心库定义了两个资源接口：

public interface Disposable {
    public fun dispose()
}

public interface Closeable : Disposable {
    public fun close()
    public override fun dispose() { close() }
}
  • 具有“关闭”语义的对象——文件、套接字、流、原生句柄——实现 Closeable，以 close() 为主入口；
  • 取消登记、锁、线程等其他资源实现 Disposable.dispose()；
  • close/dispose 是同步方法，可以阻塞或抛出异常。实现者在完成释放后，重复调用应当没有效果。

use

扩展函数 use 把正文交给资源执行，并保证无论正文正常返回还是抛出异常，都恰好调用一次 dispose()：

class Connection(val name: String) : Closeable {
    public override fun close() {
        println(f"closed ${name}")
    }
}

fun main() {
    val length = Connection("db").use { conn ->
        println(f"using ${conn.name}")
        conn.name.charLength
    }
    println(length)
}
正文清理结果
返回 r成功返回 r
抛出 p成功重新抛出 p
返回 r抛出 c抛出 c
抛出 p抛出 c抛出 ResourceUseException，其 primaryFailure 为 p、cleanupFailure 为 c
  • 挂起版本 suspend fun <T : Disposable, R> T.use(block: suspend (T) -> R): R 在正文挂起期间保持资源存活，恢复后的正常或异常退出才清理；取消按普通异常处理。
  • 需要挂起才能完成的清理（例如异步刷新并关闭连接）使用 scoop.asyncio 的 AsyncCloseable 与 useAsync。
  • use 是普通的函数调用：正文是 lambda，不能用裸 return 返回外层函数。嵌套的 use 按由内到外的顺序清理。
  • 获取资源的表达式（use 的接收者）本身抛出异常时，没有资源需要清理。

库的命名约定：withX { … } 表示在作用域内借用资源，takeX() 表示取走当前所有者持有的资源，接管外部资源的工厂命名为 takeOwnership。

GC 与 release

Scoop 没有终结器或析构函数，对象不可达时不会执行任何托管回调。直接持有原生资源的 final class 可以声明 release { … } 块作为遗漏 close 时的兜底；它不保证执行时机，确定性释放仍然依靠 close、use 与 try/finally。
