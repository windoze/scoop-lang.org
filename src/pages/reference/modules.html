Cone、package 与 import

Cone 是 Scoop 的模块、依赖、编译与链接单位；package 只是源码的命名空间。一个 Cone 可以包含多个 package，package 与目录结构无关。internal 可见性的边界就是 Cone。

Cone

  • 每个 Cone 有唯一的坐标 group:name:version，例如 dev.example:server:0.1.0。group 与 name 由点分隔的小写 ASCII 段组成（每段匹配 [a-z][a-z0-9-]*），version 是精确的 SemVer。版本是身份的一部分：同一份源码的两个版本是不同的 Cone。
  • Cone 分为 library 与 executable。一个程序恰好有一个 executable 根，其余都是 library；executable 不能被依赖。
  • 依赖图必须无环，同一个程序中同一 group:name 只能有一个版本。
  • 每个 Cone 编译为一个 .slib 产物；下游 Cone 通过 .slib 完成类型检查、泛型实例化与链接，不需要重新读取依赖的源码。

Cone.toml

多文件项目是一个包含 Cone.toml 的目录，用 scoop new --group dev.example app 创建：

schema = 1

[cone]
group = "dev.example"
name = "server"
version = "0.1.0"
kind = "executable"          # 或 "library"

[dependencies]
"scoop:scoop.std" = "0.1.0"                                         # 随工具链发布的系统库
"scoop:scoop.json" = "0.1.0"
"dev.example:model" = { path = "../model" }                         # 本地源码
"org.example:http" = { github = "example/http", tag = "v1.2.0" }    # Git / GitHub
"org.example:log" = { version = "1.4.0", registry = "https://packages.example.org/" }
"org.vendor:codec" = { version = "=2.0.1", artifact = "../artifacts/codec.slib" }

[test-dependencies]
"scoop:scoop.test" = "0.1.0"
  • schema 与 [cone] 的四个字段必需；可选的 license、repository、description、readme 只用于发布和文档。未知字段是错误。
  • 除 core 外，没有隐式依赖：manifest Cone 只自动依赖核心库 scoop.core，使用 scoop.std 及其他库都需要显式声明。依赖本身不导入任何名称，仍需 import。
  • group = "scoop" 且没有指定来源的依赖从工具链的 sysroot 中查找；其他没有指定来源的依赖使用配置的默认 registry。
  • scoop pm 解析整个依赖闭包并写入 Cone.lock，构建只消费其中的精确选择；scoop build/run 在需要时自动准备。常用命令有 scoop pm add/remove、resolve、fetch、update 与 deps --why。

版本要求

声明允许的版本
"1.4.0" 或 "^1.4.0">=1.4.0, <2.0.0
"0.3.2">=0.3.2, <0.4.0
"~1.4.2">=1.4.2, <1.5.0
"=1.4.2"只有该版本
">=1.4.0, <1.8.0"各比较项的交集

版本号必须写全 major.minor.patch；没有 latest、通配符或“或”表达式。artifact 来源要求精确版本。来源与求解细节、workspace 与 registry 见registry 指南与包管理规范。

workspace

多个 Cone 可以组成 workspace：根清单的 [workspace] 列出 members 与可选的 default-members，成员可以用 { workspace = true } 继承 group、version 等字段以及 [workspace.dependencies] 中的依赖声明。命令行用 --workspace 或 -p group:name 选择成员。workspace 中的每个程序独立求解依赖，可以使用不同的版本。

源码选择与平台条件

默认情况下，Cone 的源码是 src/ 下所有 .scoop 文件。出现 [[sources]] 时，它就是完整的源码清单，可以用 when 按构建目标选择：

[[sources]]
path = "src/common"

[[sources]]
path = "src/os/linux"
when = { os = "linux" }

[[sources]]
path = "src/os/darwin"
when = { os = "darwin" }
  • when 支持 os（darwin、linux、windows）、arch（aarch64、x86_64）与 env（none、gnu、musl、msvc-ucrt、llvm-mingw-ucrt、llvm-mingw-msvcrt）；多个键取“与”，同一键的数组取“或”。条件按构建目标而不是宿主求值。各目标对应的取值见构建目标。
  • 选中的路径不能重叠或重复；最终源码为空是构建错误。文件按完整相对路径排序，编译结果不依赖文件枚举顺序。
  • Scoop 没有文件内的条件编译或 expect/actual：平台差异通过按目标选择源码目录来表达。
  • C/C++ 源码与系统库在 [native] 中配置，见原生互操作。

Windows 可执行程序

executable Cone 可以用 [windows] 节配置 Windows 程序的 PE 子系统与资源：

[windows]
subsystem = "gui"            # "console"（默认）或 "gui"
rc = "resources/app.rc"      # 可选：相对 Cone 根的资源脚本（图标、版本信息等）
  • 只作用于 Windows 目标，其他目标不读取 RC 文件；library Cone 使用该节、未知字段或非法取值都是清单错误。
  • gui 程序启动时不打开控制台窗口，运行时也不会为它自动分配控制台；两种子系统使用相同的 main、命令行参数与退出码规则，都不会隐式启动窗口库或消息循环。
  • RC 脚本按 UTF-8 读取，用所选 Windows 目标的 Clang 预处理器和头文件编译，包含路径还包括本 Cone 的 native.include；c_flags 不作用于 RC。编译结果保存在 executable 的 .slib 中，只链接已有产物时不需要 RC 源码。
  • 测试程序与单文件程序总是 console 子系统，不继承生产程序的 GUI 设置或资源。

测试配置

测试源码默认位于 tests/（可用 [[test.sources]] 改变），测试专用依赖写在 [test-dependencies]。普通构建不读取、不检查测试源码与测试依赖；测试构建把生产与测试源码合并为同一个 Cone，测试代码可以访问 internal 声明，生产代码看不到测试声明。见测试库。

package

文件开头的 package 声明该文件中的顶层声明所属的命名空间。文件的结构固定为：可选的 package、若干 import、声明。

  • manifest Cone 的每个源文件必须声明 package，且 package 必须等于 Cone 的 group 或以它为前缀：group dev.example 允许 dev.example 与 dev.example.http，不允许 dev.examples 或 other。group 中带连字符的段用反引号书写，例如 package dev.`my-team`。
  • 文件路径不决定 package；同一 Cone 的所有文件一起编译，彼此之间没有顺序。
  • 不同 Cone 可以向同名 package 贡献声明（split package），但这不授予额外的可见性，来自不同 Cone 的同名声明仍是不同的实体。
  • 单文件模式不需要 package；写了 package 时编译器给出警告并忽略它。

import

import scoop.collections.*                      // 导入 package 中的全部名称
import scoop.time.Duration                      // 导入单个名称
import scoop.collections.HashMap as Map         // 导入并改名
import Color.*                                  // 导入 enum 的全部变体

enum Color { Red, Green }

fun main() {
    val counts = Map<String, Int>()
    counts["red"] = 1
    val c: Color = Red
    println(f"${counts.size} ${c == Color.Red}")
}
  • import 可以指向当前 Cone 中可访问的声明、直接依赖的 public 声明及其 re-export，以及核心库。间接依赖的 package 不能直接导入，需要在自己的清单中声明为直接依赖。
  • 选中一个类型后可以继续导入它的嵌套声明、object 与 companion 成员，以及 enum 变体（import E.*）。
  • 通配 import 不能带 as。同一名称经不同路径导入到同一个声明时视为同一个；来自不同 Cone 的同名不可重载声明在同一层相遇是歧义错误。
  • 表达式中不能直接写包名：scoop.compiler.env("X") 不是合法的调用，应先 import scoop.compiler.env 再调用 env("X")；函数引用同样写作导入后的 ::env。
  • 核心库的 prelude 默认可见：println、Option 及 Some/None、ArrayList、StringBuilder、Closeable 等，见核心库。

块级 import

代码块中也可以写 import，作用范围从该语句之后到块结束，可以被嵌套块继承：

fun buildTag(): String {
    import scoop.compiler.env
    return env("SCOOP_BUILD_TAG") ?: "dev"
}

fun main() {
    println(buildTag())
}

块级 import 只影响编译期的名称查找；内层块的 import 优先于外层块。public import 只能写在文件头。

re-export

public import 除了在当前文件中导入名称，还把目标以当前文件的 package 重新导出给依赖当前 Cone 的代码：

package dev.example.api

public import dev.example.model.User           // 下游可以写 import dev.example.api.User
public import dev.example.model.Order as PurchaseOrder
  • 只能 re-export 依赖中的 public 声明，不能 re-export 当前 Cone 自己的声明。
  • re-export 只建立新的名称，不创建包装或副本，导入方得到的是同一个实体。re-export 可以成链。
  • 公开 API 签名中引用的依赖类型，即使没有 re-export，下游也能正常使用；只是不能直接写出它的短名称。希望下游只依赖当前 Cone 时，请显式 re-export。

名称查找顺序

没有显式接收者的名称按以下顺序查找，越靠前优先级越高：

  1. 局部变量、参数与局部函数；
  2. 隐式 this 的成员；
  3. 已生效的块级 import（由内到外；同一块中具体名称先于通配）；
  4. 当前文件的具体 import（含别名与 public import）；
  5. 当前 package 中可访问的声明；
  6. 当前文件的通配 import；
  7. 核心库 prelude；
  8. 期望类型唯一确定的 enum 中的同名变体。

带显式接收者的调用先查真实的成员，再按同样的作用域顺序查扩展。对函数调用，编译器只在第一个含有适用候选的层中做重载选择；高层只有同名但不适用的函数时继续查下一层。类型、object、属性等不能重载的名称在同一层出现多个来源时是歧义错误。依赖的声明顺序、re-export 链的长短都不影响结果。

程序入口

executable 的根 Cone 必须恰好有一个顶层的普通 main 函数（非泛型、非挂起），签名为以下之一：

签名正常结束时的退出码
fun main()0
fun main(args: Array<String>)0
fun main(): Int返回的值
fun main(args: Array<String>): Int返回的值
  • main 不需要是 public；依赖中的 main 不参与入口选择，library 中名为 main 的函数只是普通函数。
  • args 包含完整的原生 argv：args[0] 是程序自身的启动路径，用户参数从 args[1] 开始。这与 Java/Kotlin 不同。参数保持原有顺序，空字符串也会保留。
  • 参数按严格 UTF-8 解码；含非法 UTF-8 时程序以退出码 1 启动失败，不调用 main。Windows 的原生参数是 UTF-16，先无损转换为 WTF-8，因此含非配对 surrogate 的参数（包括 args[0]）同样导致启动失败。需要原始参数的程序使用无参数的 main 并通过 scoop.platform 读取（Windows 上得到保留全部 UTF-16 code unit 的 OsString）。
  • 返回 Int 的 main 可以返回任何 Int；POSIX 系统上父进程通常只能看到低 8 位，Windows 保留完整的 32 位退出码。未捕获异常、启动失败与 trap 都以退出码 1 结束。
  • main 返回时仍有未 join 的线程或未释放的原生回调，是关闭失败，程序以退出码 1 结束。
fun main(args: Array<String>): Int {
    if (args.size < 2L) {
        println("usage: greet NAME")
        return 2
    }
    for (i in 1L until args.size) println(f"Hello, ${args[i]}!")
    return 0
}
$ scoop run --release greet.scoop -- Ada Lin
Hello, Ada!
Hello, Lin!

单文件模式

scoop run file.scoop 与 scoop build file.scoop 把指定的文件当作一个只含该文件的可执行 Cone：

  • 默认依赖 scoop:scoop.core:0.1.0 与 scoop:scoop.std:0.1.0；
  • 额外依赖写在文件头部的 //! dep: group:name:version 行注释中（在第一个语言记号之前，可以有多行），只能使用精确坐标，从 sysroot 或显式的 artifact 路径查找；
  • 不读取旁边的 Cone.toml、其他源文件或 C 源码，package 声明被忽略；
  • 首行可以是 #! 解释器行，见词法结构。
//! dep: scoop:scoop.json:0.1.0

import scoop.json.*

fun main() {
    println(Json.stringify(Json.parse("[1, 2, 3]")))
}

构建目标

Scoop 的目标名同时确定架构、操作系统、原生工具链环境与 C 运行时。不同目标的 .slib、运行时和缓存互不相容；用 --target 选择目标，省略时使用宿主的默认目标。

目标os / arch / env说明
aarch64-apple-darwindarwin / aarch64 / nonemacOS，Apple Clang 与系统 SDK
x86_64-unknown-linux-gnulinux / x86_64 / gnuLinux glibc，默认动态链接
x86_64-unknown-linux-musllinux / x86_64 / muslLinux musl，默认静态链接
x86_64-pc-windows-msvc-ucrtwindows / x86_64 / msvc-ucrtWindows 默认目标：Microsoft SDK/MSVC 工具集（cl 或 clang-cl）、UCRT、MSVC STL
x86_64-w64-windows-llvm-mingw-ucrtwindows / x86_64 / llvm-mingw-ucrtLLVM-MinGW、UCRT、libc++
x86_64-w64-windows-llvm-mingw-msvcrtwindows / x86_64 / llvm-mingw-msvcrtLLVM-MinGW、旧版 msvcrt.dll、libc++
  • Windows 目标必须写完整名称，没有 windows-ucrt 这类简称，也不会根据本机恰好安装的编译器改选目标。三个 Windows 目标生成 Win64 ABI 的 PE32+ 程序，要求 Windows 10 x64 及以上；它们之间的产物不能混用，即使 CRT 相同。
  • Windows 目标的可执行文件默认名追加 .exe（包括测试程序），显式 -o 的路径保持原样。
  • Windows 目标动态依赖所选 CRT，--link-mode static 不适用。使用 C++ 的 MSVC 程序部署时需要附带实际依赖的 VCRuntime/MSVC STL DLL。

初始化顺序

  • 需要运行期计算的顶层属性在进入 main 之前初始化。Cone 按依赖优先的拓扑顺序处理，平级的按坐标排序；同一 Cone 内的顺序由声明的身份决定，与文件书写顺序无关。
  • 初始化中读取另一个尚未初始化的属性时，会先完成那个属性的初始化。直接的初始化依赖环是编译错误，经函数调用形成的间接环在运行期报错。
  • object 与 companion 在首次访问时初始化，见 object 与 companion。
  • 任何启动初始化失败时不执行 main，程序以退出码 1 结束。
